# App SDLC

## Purpose

`app-sdlc` is the top-level orchestrator for a project. It converts a broad product goal into independently verifiable features, coordinates work, routes failures to the right workflow, and stops at evidence-backed acceptance.

The skill owns sequencing, state, quality gates, and human gates. Domain skills own detailed implementation methods.

## Invocation

Use this skill when the request is one of:

- build or extend a product
- plan an app or a product roadmap
- add a group of related features
- run an end-to-end AI delivery workflow
- resume work from an existing intent, spec, plan, or issue

Route a confirmed defect directly to `bug-fix`. Route a single small, unambiguous change directly to the relevant implementation skill.

## Operating state

Maintain project state under `.sdlc/`:

```text
.sdlc/
├── intent.md
├── roadmap.md
├── stack.md               ← detected project stack (written at intake)
├── features/
│   └── <feature-name>/
│       ├── spec.md
│       ├── plan.md
│       ├── acceptance.yaml   ← machine contract; the only authority on done
│       ├── ownership.json     ← paths this lane may edit
│       ├── evidence.md       ← human summary; per-feature, never shared
│       ├── evidence.json     ← generated by sdlc-verify
│       └── status.json       ← generated by sdlc-verify
├── status.md
├── decisions.md
└── evidence.md            ← integration-level evidence only (step 5)
```

`status.json` and `evidence.json` are generated. Never hand-edit them, and never
write `accepted` into any file yourself. Read `${AI_SKILLS_HOME}/skills/app-sdlc/references/state-schema.md`
for the phase machine, the legal transitions, and the blocked-reason vocabulary.

Do not create planning files for a trivial change. For a full product effort, keep the files small, current, and traceable.

## Workflow

### 1. Intake and alignment

1. **Detect the project stack.** Before asking any questions, inspect the repository for:
   - `package.json` (Node/JS framework: Next.js, React, Vue, Express, etc.)
   - `pyproject.toml`, `setup.py`, `requirements.txt` (Python)
   - `Cargo.toml` (Rust)
   - `go.mod` (Go)
   - `build.gradle`, `pom.xml` (JVM)
   - `*.config.ts/js` (Vite, Webpack, Tailwind, etc.)
   - `.env.example` or `docker-compose.yml` (infrastructure hints)
   Record the detected stack, runtime, test framework, and build tool in `.sdlc/stack.md`. Use this to inform default validation commands and which optional skills to activate (e.g. `pct102-frontend-patterns` for React/Next.js projects).

2. Read the repository guidance and current `.sdlc/` state.
3. Inspect the codebase before asking questions that the repository can answer.
4. Use `pct102-brainstorm` to classify the work as spike, bounded, or architectural before implementation planning.
5. Use `pct102-jev` to classify the first unresolved branches: blocking, user-choice, or deferrable. Jev selects the question path; it does not answer the user's product question.
6. Use `pct102-grill-me` to interview the user, or run the fallback interview in `${AI_SKILLS_HOME}/skills/app-sdlc/references/quality-gates.md`.
7. Ask one decision-bearing question at a time.
8. Record the goal, users, constraints, non-goals, risks, and acceptance outcomes in `intent.md`.
9. Stop for user confirmation when product direction, budget, security posture, or destructive scope is unresolved.

Do not start implementation while the goal or acceptance outcomes are ambiguous.

### 2. Feature decomposition

Break the approved intent into vertical features. A feature must have observable value and an independent verification path.

For every feature record:

- outcome and user value
- dependencies
- affected boundaries
- acceptance criteria
- validation command
- owner or execution lane
- risk level

Each feature gets its own `acceptance.yaml` and `ownership.json` before any implementation starts, and its own `status.json`. A feature with no acceptance contract cannot be dispatched, because there is nothing for the lane to prove when it finishes.

Put independent features in parallel lanes. Put dependent features in a dependency graph. Every parallel feature lane writes only inside its own `.sdlc/features/<feature-name>/` and only touches the paths in its `ownership.json`.

Do not decide by hand which lanes may run together. Ask the dispatcher, which compares the static directory prefixes in every `ownership.json` and admits the non-overlapping set:

```bash
node ${AI_SKILLS_HOME}/tools/sdlc-dispatch.mjs
```

A lane reported with `file_conflict:<lane>` must not start. Narrow its `owns` to what the feature genuinely edits, or sequence it after the blocking lane.

### 3. Feature execution

After design approval, use the installed `using-git-worktrees` and `writing-plans` skills from `obra/superpowers` when available. For architectural work, use `${AI_SKILLS_HOME}/references/archify.md`; for high-risk plans, use `${AI_SKILLS_HOME}/references/claudex-loop.md`; for external skills, run the `${AI_SKILLS_HOME}/references/skillspector.md` gate. Dispatch each feature to `feature-lifecycle` when it needs a full spec, implementation, and validation loop. Use `subagent-driven-development` or `executing-plans` for the bounded implementation loop. Keep the main session focused on decisions, integration, and evidence.

A lane declares what it is about to do before it starts, so an interrupted run is resumable:

```bash
node ${AI_SKILLS_HOME}/tools/sdlc-verify.mjs --feature <name> --set-phase building
```

Each feature must finish with a green verifier run, not a self-reported success claim:

```bash
node ${AI_SKILLS_HOME}/tools/sdlc-verify.mjs --feature <name>
```

The main session does not run the lanes itself in the default configuration. It asks the
dispatcher which lanes may start, and passes it the command that starts one:

```bash
node ${AI_SKILLS_HOME}/tools/sdlc-dispatch.mjs --exec '<command with {feature} and {worktree}>'
```

Without `--exec` the dispatcher only prints the plan and changes nothing.

### 4. Failure routing

When a test, lint, typecheck, build, security check, or runtime check fails:

1. Classify it as a confirmed product defect, a flaky or environmental failure, an invalid test, or a missing requirement.
2. Route confirmed defects to `bug-fix`.
3. Route invalid tests to the owning feature workflow and revise the acceptance contract explicitly.
4. Route environmental failures to environment repair; do not modify production logic to hide them.
5. Route missing requirements back to alignment and planning.

Do not use `bug-fix` for a feature that has not been designed.

### 5. Integration and release

After feature lanes finish:

1. Reconcile interfaces, migrations, contracts, and shared state.
2. Re-run the full project validation suite through the owning features' `acceptance.yaml`. A green per-feature run does not prove the integrated build; add an integration check to a contract before trusting it.
3. Review the integrated diff for scope, security, and regressions.
4. Use `verification-before-completion` and the finishing-a-development-branch workflow when available.
5. Use `${AI_SKILLS_HOME}/references/playwright-mcp.md` for user-facing runtime or visual verification when applicable.
6. Use `${AI_SKILLS_HOME}/references/slopmonster.md` for English user-facing copy when applicable.
7. Deploy only to an approved environment.
8. Record integration evidence in `.sdlc/evidence.md`, citing the per-feature `status.json` files it rests on.

Production deployment, destructive data actions, billing changes, credential changes, and broad architecture changes require explicit human approval, recorded as a `kind: manual` check so that a feature cannot reach `accepted` while one is outstanding.

## Loop and stop conditions

Use a bounded loop:

```text
align → decompose → build → validate → route failures → integrate → verify
```

The loop is bounded by machine, not by intention. `sdlc-verify` counts failed validations
against the feature's `budget` and moves the lane to `escalated` on its own. Read
`${AI_SKILLS_HOME}/skills/app-sdlc/references/state-schema.md` for the phase machine.

Default repair budget: two failed validations per feature, set as `budget` in the
feature's `acceptance.yaml`. A bug may use three diagnosis/fix iterations when the failure
is intermittent. Exhaustion is an escalation, not a success. Do not reset a budget to keep
a loop alive; `--reset-repair` is a triage decision and belongs to the user.

Stop and ask the user when:

- product intent changes
- a dependency contract conflicts
- `status.json` shows `escalated` for a lane you cannot fix
- `status.json` shows `blocked` on a `manual` gate
- a fix would expand scope beyond the approved feature
- validation depends on unavailable credentials or infrastructure
- a destructive or production action is proposed

Report the lane's `blocked_reason` verbatim. Do not paraphrase it, and do not treat an
`escalated` lane as finished because the last run happened to pass after a manual edit.

## Scheduled resume

Once lanes exist, the loop can run without a session open. Ask for the resume pass, not a
fresh plan:

```bash
bash ${AI_SKILLS_HOME}/tools/sdlc-resume.sh --run --exec '<command with {feature} and {worktree}>'
```

It does one thing per lane, chosen from `status.json`: re-verify a `validating` lane,
restart a `building` lane through the dispatcher, and leave `planned`, `accepted`,
`blocked`, and `escalated` alone. It never starts work that was never begun and never
resets a repair budget.

Its exit code tells the operator what happened: `2` the loop did work, `1` something needs
a human, `0` nothing to do. `escalated` and `blocked` lanes are the only things that should
ever reach a human through this path.

Without `--run` it only prints the plan. Use `--run` alone with no `--exec` to re-verify
without restarting any lane.

This is a schedule, not a trigger. Nothing here watches for a pull request, an alert, or a
webhook. Event-driven dispatch is a later step, not part of this loop.

To run automatically on a recurring basis, use the `schedule` skill:

```
/schedule: every day at 9am — run sdlc-resume on <project>
Command: bash ${AI_SKILLS_HOME}/tools/sdlc-resume.sh --run --exec '<lane start command>'
```

The scheduled agent reads `.sdlc/roadmap.md` and each feature's `status.json` on cold
start, then invokes `sdlc-resume.sh`. Exit code `1` or `2` items are reported to the user;
exit code `0` (nothing to do) produces no notification.

**Cold start (no active session context):** Read `.sdlc/intent.md` for the project goal,
`.sdlc/roadmap.md` for the feature queue, and `.sdlc/features/<name>/status.json` for each
listed feature before running any tool. Do not re-run intake or re-ask alignment questions
that are already recorded in `intent.md`.

## Completion report

Report:

- status: `accepted` | `escalated` | `blocked`, taken from each `status.json`
- completed features
- validation results, taken from each `evidence.json`
- evidence paths (per-feature and integration)
- remaining risks
- smallest required human decision, if any
- follow-up work, if any

Never report `accepted` when any `status.json` says otherwise, and never report `accepted`
because you believe the work is done.

## Dependencies

Read `${AI_SKILLS_HOME}/references/dependencies.md` when selecting helper skills. Use optional skills such as `pct102-grill-me`, `pct102-brainstorm`, `pct102-ponytail`, `pct102-tdd`, `pct102-jev`, and `pct102-review-code` as capabilities, not as mandatory duplicated procedures.

`${AI_SKILLS_HOME}/tools/` is the machine layer and is not optional: `sdlc-verify.mjs` decides acceptance, `sdlc-dispatch.mjs` decides which lanes may run in parallel, and `sdlc-resume.sh` restarts interrupted lanes. If these are missing, report the workflow as unavailable rather than falling back to a self-reported verdict.

Run `bash ${AI_SKILLS_HOME}/tools/selftest/run-all.sh` after changing anything in `tools/`. Those tests are the reason the machine layer can be trusted; a change that breaks them has broken the guarantee that `accepted` means verified.
