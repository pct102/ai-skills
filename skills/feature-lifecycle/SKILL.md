# Feature Lifecycle

## Purpose

Deliver one independently verifiable feature without drifting into unrelated work. This workflow owns the feature contract, implementation loop, and acceptance evidence. It delegates detailed methods to reusable skills.

## Inputs

Require an approved feature outcome, affected boundary, acceptance criteria, validation commands, and risk level. If these are missing, return to `app-sdlc` alignment.

## Evidence path

All feature evidence is written to `.sdlc/features/<feature-name>/evidence.md`. Never write to a shared top-level evidence file — parallel feature lanes must not overwrite each other.

`evidence.md` is written for a human reader. It is **not** evidence of anything on its own: `evidence.json` and `status.json` are generated by `sdlc-verify` and are the only authoritative record. Copying command output into `evidence.md` by hand is never sufficient.

## Workflow

### 1. Feature contract

Create or update:

```text
.sdlc/features/<feature-name>/spec.md
.sdlc/features/<feature-name>/plan.md
.sdlc/features/<feature-name>/acceptance.yaml
.sdlc/features/<feature-name>/ownership.json
.sdlc/features/<feature-name>/evidence.md      ← human summary, written last
.sdlc/features/<feature-name>/evidence.json    ← generated by sdlc-verify
.sdlc/features/<feature-name>/status.json      ← generated by sdlc-verify
```

The contract must state:

- user-visible outcome
- in-scope and out-of-scope behavior
- interfaces and data boundaries
- error and empty states
- security and privacy constraints
- acceptance criteria
- validation commands

Translate the acceptance criteria and validation commands into `acceptance.yaml` before writing any implementation code. Start from `${AI_SKILLS_HOME}/skills/feature-lifecycle/references/acceptance-template.yaml`.

Rules for `acceptance.yaml`:

- Every deterministic check the feature must pass gets an entry with a runnable `cmd` and `kind`.
- A step that only a human can confirm (a deployment target, a visual sign-off, a legal or billing decision) becomes a `kind: manual` entry with a `desc`. It is never auto-passed.
- If a check is not applicable to this feature, delete it. Do not add a check that always passes.
- Never weaken a `cmd` so that it passes. A check that no longer describes the requirement belongs in the contract revision, not in a relaxed command.

Declare the files this lane owns in `ownership.json`, starting from `${AI_SKILLS_HOME}/skills/feature-lifecycle/references/ownership-template.json`. List directories with a static prefix (`src/auth/**`), not bare file patterns, because a pattern with no directory prefix is treated as a catch-all and will collide with every other lane. Ownership is what makes a parallel lane safe; see step 2.

**If the feature has UI or frontend scope**, invoke `pct102-frontend-patterns` now to inspect the product surface, identify design tokens and existing components, and agree on the component approach before writing implementation code. Record the component contract in spec.md.

For architectural changes, use `${AI_SKILLS_HOME}/references/archify.md` to create a validated architecture or sequence artifact. For an authorized visual reference, use `${AI_SKILLS_HOME}/references/site-clone.md`. For external skills or MCP servers, apply `${AI_SKILLS_HOME}/references/skillspector.md` before installation.

Do not write implementation code while the contract contains unresolved product decisions.

### 2. Plan and dependency map

Break the feature into small tasks. Each task must identify files or boundaries, dependencies, tests, validation, and completion evidence.

Use `writing-plans` from `obra/superpowers` when available. Use the plan template in `${AI_SKILLS_HOME}/skills/feature-lifecycle/references/plan-template.md` when a project does not already have a planning format.

Run independent tasks in parallel only when they do not edit the same state or interface. Sequence tasks that share a contract, migration, generated client, or public API.

When this feature runs alongside others, do not reason about collisions by reading `plan.md`. Ask the dispatcher:

```bash
node ${AI_SKILLS_HOME}/tools/sdlc-dispatch.mjs
```

It admits the lanes whose `ownership.json` prefixes do not overlap and defers the rest with a `file_conflict:<lane>` reason. If this feature is deferred, do not start it. Either narrow `owns` to what the feature really edits, or wait for the blocking lane. A bare `**` in `owns` is always deferred.

Use `pct102-jev` only to classify a concrete routing choice such as parallel versus sequential; do not infer the dependency graph from a score.

### 3. Test-first implementation

For behavior changes, use the installed `test-driven-development` or `tdd` skill when available. Otherwise follow the same contract:

1. Add the smallest test that captures the requested behavior.
2. Run it and confirm the test fails for the intended reason.
3. Implement the minimum change.
4. Run the focused test.
5. Refactor only while the focused and relevant tests remain green.
6. Run the full feature validation set.

Do not weaken or delete a test merely to make it pass. If the expectation is wrong, return to the feature contract.

### 4. Validation

The gate order and the project's declared commands come from `${AI_SKILLS_HOME}/skills/app-sdlc/references/quality-gates.md`. Encode the applicable steps as `acceptance.yaml` checks, then run the gate through the verifier:

```bash
node ${AI_SKILLS_HOME}/tools/sdlc-verify.mjs --feature <feature-name>
```

Do not hand-run the checks and declare the result. The verifier owns the verdict, writes `evidence.json`, and advances the state machine.

Its exit codes are the contract:

| exit | meaning | required response |
| --- | --- | --- |
| 0 | every check passed | continue to step 5 |
| 1 | at least one check failed | classify the failure, fix, re-run |
| 2 | automatic checks pass, a `manual` gate is unapproved | surface the gate to the user |
| 3 | the contract or state is invalid | fix the contract; do not retry blindly |

Use `${AI_SKILLS_HOME}/references/playwright-mcp.md` for live journeys and visual checks, and `${AI_SKILLS_HOME}/references/slopmonster.md` for English user-facing copy. Add each of them to `acceptance.yaml` as a check so their result is recorded too.

When a check fails, classify the failure rather than retrying blindly. Confirmed defects route to `bug-fix`; an invalid requirement returns to this contract, which means revising `acceptance.yaml` and saying so; an environmental failure stays an explicit blocker. `sdlc-verify` counts failed runs and escalates on its own once the repair budget is spent, so do not keep re-running a lane that is already `escalated`.

### 5. Review and evidence

Review the final diff for:

- scope creep
- API and data contract changes
- error handling
- security and privacy
- accessibility where user-facing
- migration and rollback risk
- missing tests

Use the installed `requesting-code-review` or `code-review` skill when available. Summarize the recorded result in `evidence.md` and cite `evidence.json` as the source. Do not restate a check as `pass` in `evidence.md` unless `evidence.json` says so.

## Optional discipline

Use `pct102-ponytail` as a scope discipline: prefer the smallest solution that satisfies the contract, but preserve security, accessibility, and required observability. Use `pct102-jev` only for bounded classification, scoring, or routing judgments with explicit criteria. For high-risk or architectural work, use `${AI_SKILLS_HOME}/references/claudex-loop.md`; for selected specialist roles, use `${AI_SKILLS_HOME}/references/gstack-patterns.md` or `${AI_SKILLS_HOME}/references/agency-agents.md`. Neither replaces deterministic tests.

## Human gates

Human approval is recorded as a `manual` check in `acceptance.yaml`, not as an aside in a report. Record the approval with:

```bash
node ${AI_SKILLS_HOME}/tools/sdlc-verify.mjs --feature <feature-name> --approve <check-id> --by <name>
```

The verifier re-runs the whole contract after recording an approval, so `evidence.json` never mixes a fresh gate with stale check results.

A `manual` gate is required for: production deployment, destructive data operations, credential or billing changes, public contract changes, and broad architecture changes. Ask before changing product behavior and stop rather than inventing a requirement.

## Completion report

A feature is complete only when:

- the contract is approved
- all planned tasks are accounted for
- required tests pass
- lint, typecheck, and build pass or are explicitly not applicable
- the diff is reviewed
- acceptance criteria have evidence
- known risks are recorded

Then confirm the machine state, which is the only authority:

```bash
node ${AI_SKILLS_HOME}/tools/sdlc-verify.mjs --feature <feature-name>
```

Report:

- status: `accepted` | `blocked` | `escalated`, taken from `status.json`
- completed tasks
- validation results, taken from `evidence.json`
- evidence paths: `evidence.md` for a human, `evidence.json` and `status.json` for the record
- remaining risks
- smallest required human decision, if any
- follow-up work, if any

If `status.json` says `blocked`, name the pending gate. If it says `escalated`, name the exhausted budget and the failing check ids. Report `accepted` only when `status.json` says `accepted`; never report it from your own reading of the diff.
